# AI assistants (MCP)

The MCP server at /mcp: auth, tokens, OAuth, tools and their rules. Dates in headings are when a decision was made. Moved out of CLAUDE.md on 2026-11-07; the rules summary is in `AGENTS.md`.

## MCP server (AI assistants)

`app/mcp_server/` serves an MCP server at `/mcp` (Streamable HTTP, **stateless with JSON responses**, so any worker can answer any request) built on the official `mcp` SDK (2.x: `MCPServer`, not `FastMCP`). It is a plain ASGI route added in `app/main.py`, and `main.lifespan` runs the SDK's session managers (`transport.lifespan` builds fresh ones on every start, because tests start the app many times).

- **Auth (phase 1):** personal access tokens (`api_tokens`: only a sha256 of the `fin_…` secret is kept, plus a display prefix, scope `read`/`write`/`manage` (`TokenScope`, with `can_write` / `can_manage`; `manage` is write plus changing accounts, never deleting them; the CHECKs on `api_tokens` and `oauth_grants` allow it since migration `d3f5b7c9e1a2`), last used, revoked). Users create and revoke them on `/profile/assistants` (the finode app: `/api/assistants/…`, cookie session only, see `docs/developer/api.md`); the secret is shown once. `transport.MCPEndpoint` checks the bearer token, applies a per-token per-process rate limit (`settings.mcp_rate_limit` a minute), puts the `TokenOwner` in `context.current_owner` and hands the request to the server for that scope: read-only tokens get a server whose write tools are still listed but only refuse, telling the assistant to ask the user to allow read & write under Profile › AI assistants (`tools._refused`). Tokens only work on `/mcp`, never on the JSON API, and cannot manage tokens. - **OAuth (phase 2, for claude.ai, the Claude mobile app and other connectors):** Supabase's OAuth 2.1 server (Authentication › OAuth Server in the dashboard: enabled, authorization path `/oauth/consent`, dynamic client registration on) registers the apps, runs the sign-in and issues their access tokens; finode never issues tokens. `/.well-known/oauth-protected-resource[/mcp]` (RFC 9728, `transport.protected_resource_metadata`) names Supabase as the authorization server, and every 401 from `/mcp` carries `resource_metadata` in `WWW-Authenticate` so clients can discover it. Supabase redirects the user to `/oauth/consent?authorization_id=…` (`routers/web/oauth.py`; the finode app's screen uses `GET`/`POST /api/oauth/consent/{authorization_id}`, `routers/assistants.py`, and from step 9 Supabase's authorization path points at the app; `app/oauth.py` calls `/auth/v1/oauth/authorizations/{id}` and `…/consent` with the user's own session token); the user picks read-only or read & write and the choice is stored in `oauth_grants` (per user and Supabase `client_id`: Supabase has no read/write scope). On `/mcp` a JWT must verify against Supabase's keys **and** carry a `client_id` **and** match a non-revoked grant of that user, which supplies the scope; ordinary sign-in tokens (no `client_id`) are refused there, and conversely an app's token is refused by the JSON API and web UI (`auth.reject_app_token`), so it can never act as a full sign-in. Disconnecting (Profile › AI assistants › Connected apps) revokes the grant and asks Supabase to revoke the app's tokens. The login page carries a `next` only for the consent page (`web_auth.safe_next`).
- **Assistants page UX:** `/profile/assistants` lists apps and tokens together (`partials/connections.html`, with Allow changes / Make read only / Allow account changes / Stop account changes on each (the `access_buttons` macro), `…/access` routes, no re-creating needed) above the two ways to connect. `partials/access.html` (`level` macro) spells out each access level and is shared by the token form and the consent page, whose buttons carry the choice (`allow-read`, `allow-write`, `allow-manage`, `deny`) instead of a radio.
- **Tools** (`tools.py`) call the same services as everything else through `context.services()` (which builds them for the token's user, like `dependencies.py`). They take account paths (`Assets:Bank:HDFC`, a unique end like `HDFC`, or other separators), resolved by `accounts.AccountIndex.find`, which explains ambiguous or unknown names. Amounts go out as strings. Service errors become `ToolError`s with the service's message. Write tools carry MCP annotations (`delete_transaction` is destructive). Assistants can create accounts; changing them (rename, move, close, reopen, merge) needs the `manage` access level, and they never delete them. Keep `INSTRUCTIONS` in step with ledger rules. **Agent-friendly work (branch `feature/agent-friendly`, plan in `docs/developer/agent-friendly-plan.md`; update the plan's status and the docs with every step):** tools print ids next to paths (accounts, postings, budget lines; an id survives renames), `get_status` says what the connection may do and how much room is left, `list_accounts` carries type, `on_budget`, group and details, and `search_transactions` pages (`offset`) and totals every match (`count`, `spent`, `earned`, `transferred`, `account_net_change`). **References (migration `c1e3a5b7d9f0`):** `transactions.source`, `external_id`, `source_url` (`ReferenceFields` in `schemas/transaction.py`; the source is lower-cased, a reference needs a source, the link must be http(s)); a partial unique index on `(user, source, external_id)`; `TransactionService.create_once` returns the existing entry when the same pair comes with the same date and rows (API 200 instead of 201, MCP `already_recorded`) and `DuplicateReferenceError` (a 400, an `InvalidPostingError`) when the content differs; `create` and `update` refuse a pair another entry has; the backup (validated: no repeated pair) and the details sheet carry them. Any new way of creating transactions that can take a reference must go through `create_once` or `create`. **Account tools (manage level):** `MANAGE_TOOLS` in `mcp_server/tools.py` (`update_account`, `close_account`, `reopen_account`, `merge_accounts`) are registered at every level but only work on `manage` connections (`_refused` with `NO_MANAGE_MESSAGE` below it); they call `AccountService.update` / `close` / `reopen`, so no rule is bypassed, and assistants still never delete accounts. A new account-changing tool belongs in `MANAGE_TOOLS`. **Merging** (`AccountService.merge`, `POST /api/accounts/{account_id}/merge`, `merge_accounts`, `dry_run` at every level): the plain source account is folded into a target of the same root that is open and postable: postings move (`TransactionRepository.repoint_account` marks each entry `updated_via`), plan rows are added by month (`BudgetRepository.merge_account`), recurring rules and payment links are re-pointed, then the source is deleted, all in one transaction; refused for opposite sides, a budget-flag mismatch, built-in groups, roots and Opening Balances. A new table or column that holds an account id must be handled there, or a merge will leave it pointing at a deleted account. **Tags:** see "Tags are their own thing, apart from the note" at the end of this file; `search_transactions` takes `tag`, `list_tags` backs on `TransactionService.tags()`. **Statement check:** `AccountService.check_balance` (statement minus books on a day, the last `days` days of entries, those as large as the difference; changes nothing) backs `GET /api/accounts/{account_id}/check-balance` and the MCP tool `check_balance`. **Payee defaults:** `TransactionService.payee_routes` (the grouping the Add screen's payee chips, `payee_habits`, and the assistants share) and `payee_defaults` (with paths and kind) back `GET /api/transactions/payee-defaults` and the MCP tool `payee_defaults`; nothing is stored. **Dry run:** `dry_run` on `POST/PATCH/DELETE /api/transactions` (`?dry_run=true`, answers `TransactionPreview`) and on `record_transaction`, `record_split`, `record_transactions`, `update_transaction`, `delete_transaction`; `preview_*` run the same checks as the real calls (`_check_new`, `_check_update` are shared, so a new rule belongs there) and save nothing; `_refused` lets `dry_run=true` through on read-only connections. A new write tool that changes a transaction should get `dry_run` the same way. **Batch:** `record_transactions` (MCP) and `POST /api/transactions/batch` (`TransactionBatch`, `BatchResult`, at most `MAX_BATCH` = 50) go through `TransactionService.record_batch`: every entry is previewed, all problems are collected by entry number, nothing is saved unless all pass, the saves share one commit (rollback on any failure), entries already recorded by reference are skipped, and the limits count the whole batch.
- **Origin:** transactions record `created_via`/`updated_via` (`web`, `api`, `import`, `mcp:<token name>`), set by `TransactionService(origin=...)` (`dependencies.get_transaction_service` decides web vs api from the path). The list marks entries made or changed by an assistant; the details sheet says who added and last changed it (`.sheet-by`, the robot, only when an assistant did one of them); the edit page says nothing (it was under Back, then under Save, and was removed 2026-10-26).
- The transaction form (`transaction_form.html`, `partials/txn_row.html`, `recomputeTxn` in `app.js`) is one page: a large **total**, then a **From** section (credit rows) and a **To** section (debit rows), each a list of account + amount rows. Each side starts with one row whose amount is the total, shown grey (a *suggestion*: a real value, class `suggested`, selected on focus so typing replaces it). When the user types a different amount in a row, it becomes theirs (`data-touched`) and a new row appears with the remainder suggested; rows are added until the side adds up and an unused suggestion row is dropped once nothing is left. At the top are the **Expense / Income / Transfer** buttons (Expense is the default; tapping the selected one again selects nothing, which offers every account and is the "other" kind) (`data-kind`, hidden `kind` field, ignored by the server; `KINDS` and `applyKind` in `app.js`): they narrow the account pickers by type (expense: from assets or liabilities to expenses; income: from income to assets or liabilities; transfer: between assets and liabilities; other: everything) by rebuilding the option lists, not hiding options, because iOS ignores hidden options. The server picks the starting kind (`infer_kind` in `routers/web/transactions.py`: expense by default, from the account when opened from one, inferred from the postings when editing, "other" when they fit none); swapping From and To, or creating an account of a type the kind does not offer, switches to "other" (or keeps "transfer"). The green "X INR allocated" line under From and To is gone (balanced is the normal state; only "left to allocate" and "over" speak, and an empty line takes no space; 2026-10-24). The swap button (`[data-swap-sides]`, `.txn-swap`) sits on the seam between the From and To tiles so both are the same height (2026-10-24). The form always saves through `/transactions/split` or `/{transaction_id}/edit` (the `total` field is ignored by the server; the older one-from-one-to routes `POST /transactions` and `/{transaction_id}/edit/simple` were removed, `simple_postings` stays for recurring rules and the assistants' `record_transaction`). `services/simple.py` turns from/to/amount into postings for both the web form and `record_transaction`; `ReportService.breakdown` (also `/reports/breakdown`) gives per-account income or expenses.
- Tests talk to `/mcp` over HTTP with the SDK client and an in-process ASGI transport (`tests/mcputil.py`: `make_token`, `running_app`, `mcp_client`, `payload`); tests are `async` with `pytest.mark.anyio`.

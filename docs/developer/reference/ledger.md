# The ledger

Accounts, transactions, postings and the rules around them: integrity, dates, currency, the four account types, cards, recurring rules, related entries and tags. Dates in headings are when a decision was made. Moved out of CLAUDE.md on 2026-11-07; the rules summary is in `AGENTS.md`.

## Double-entry ledger

`backend/finode/models/account.py` defines accounts as a tree. Each user has five system
root accounts (`Assets`, `Liabilities`, `Equity`, `Income`, `Expenses`),
created lazily on first access by `AccountService._ensure_roots` (a partial
unique index on `(user, name)` where `parent_id IS NULL` keeps this race-safe).
There is no stored type: an account's type is its root ancestor, and all
non-root accounts require a `parent_id`. Roots cannot be renamed, moved, or
deleted. A budget **category** is its own table (`budget_categories`, see "Budget categories" in [budget.md](budget.md)); an Income or Expenses account is the books' side of one.

`backend/finode/models/transaction.py` defines `Transaction` and `Posting`. A transaction
contains at least two postings, every posting has a positive amount, and total
debits must equal total credits. The service layer validates those invariants
and verifies that all referenced accounts belong to the authenticated user.
Postings may not target root accounts, except `Expenses` and `Income`
(`GROUP_POSTING_ROOT_NAMES` in `backend/finode/services/account.py`): spending and income
post to those two roots themselves and the line carries the category, so
nothing lives under them. The four account types themselves take no entries, and an
account holds no accounts (see "The four account types"); an account keeps its type.

Account balances are derived from postings. Assets and Expenses increase
with debits; Liabilities, Equity, and Income increase with credits. Asset and
liability accounts that already have postings cannot gain sub-accounts. Opening balances and
direct balance edits are posted against the system equity account named
`Opening Balances`, which cannot be renamed, moved, deleted or have its balance set directly.

## Edges of what is accepted

Checked by `backend/tests/ledger/test_ledger_edges.py`, and by `backend/tests/ledger/test_ledger_fuzz.py` (random sequences of operations, then every balance recounted from the stored postings, the trial balance, a backup and restore, and the budget's identity `ready_to_assign = money_in_accounts - reserved_for_cards - available - assigned_to_later_months`). **Dates**: every day a person can enter (a transaction, a recurring rule's start and end, a budget month, the same fields in a backup) must lie between `clock.FIRST_DAY` (1900-01-01) and `LAST_DAY` (2999-12-31): use the `Day` type in `schemas/day.py` for a new date field. Past either end the calendar arithmetic ("the month before") could fail at year 1 or 9999, and one entry dated 9999-12-31 used to turn every page into an error. `BudgetService.month_start` refuses a month outside the span (`BudgetError`, 400 in the API); `first_of_month` is the unchecked version for dates already stored. **Computed figures** (balances, totals, the budget's figures: the `Read` models) have no digit limits, because a sum of valid amounts may be longer than one amount can be (a limit there made every page an error); only an input amount is limited (16 digits before the point, 8 after, then the currency's decimals). **Text**: a NUL character cannot go into Postgres, so `models/utils` drops it from every string on every write (a `before_flush` hook) and `TransactionRepository.list` from the search text. An account's name is trimmed, visible, on one line and without `:` (`schemas/account.clean_name`), and **unique among its siblings, capitals aside** (`AccountService._check_name_free`; a journal import is case-sensitive like the format and may still create `Food` and `food`); a payee is one tidy line and a blank payee or note is none. **One entry, one direction**: an account may not be on both the debit and the credit side of one transaction (`TransactionService._resolve`; several rows of the same side are fine). **Budget**: `assign` may be negative to take back what an earlier month left in a category (that is what Move money writes too) but never more than the category has left (`BudgetService.assign`), otherwise Ready to assign would exceed the money there is.

## Ledger integrity

- **Database checks:** `postings` has `CHECK` constraints (`amount > 0`, `value > 0`, `side IN ('DEBIT','CREDIT')`), added by migration `a3c5e7f9b124`, which refuses to run if existing rows break them. Balance and "at least two postings" cannot be a plain check, so they live in `TransactionService._resolve`; `ReportService.trial_balance` (`/api/reports/trial-balance`, MCP `check_books`) re-checks every transaction from the stored rows and names the ones that fail. Any new code path that writes transactions must keep a test asserting `trial_balance().balanced`.
- **Posting ids are stable:** `TransactionRepository._replace_postings` updates postings in place on edit (matching first on account and side, then on account), adding or removing only what is left, so anything that refers to a posting keeps working.
- **No history (2026-11-05):** nothing records what happened to a transaction or account; see [removed.md](removed.md). Only `created_via` / `updated_via` say who made or last changed an entry.
- **Balances by date:** account balances count postings dated up to `as_of` (today by default, so future-dated entries do not count yet; `?as_of=` on `/api/accounts`). The register still lists every entry.

## One currency

Everyone keeps their whole ledger in **one currency**: `profiles.currency` (an ISO 4217 code, INR for new people; migration `f4b6d8a0c2e5`), chosen in Settings › Currency (`POST /settings/currency`, `PATCH /api/profile/` with `default_currency`, the field name kept for API clients). Changing it **relabels, never converts**: every stored amount stays as it is (the page says so). There are no other currencies, no assets of one's own (shares, funds, coins), no prices and no conversions; the `commodities` and `prices` tables, `accounts.commodity_id`, `transactions.currency_id` and `postings.value` were dropped. The currency list is `backend/finode/currencies.py` (`CURRENCIES`, `find`, each with its decimals and sign); `AccountService.currency()` and `TransactionService.currency()` read it for the person, and `check_places` / `TransactionService._resolve` refuse amounts with more decimals than it allows (rupees 2, yen 0, dinars 3). `Amount` columns stay `Numeric(24,8)` (read back without padding zeros: do not format money with `:.2f`, use the `money` filter or `normalize_amount`). A posting is just an `amount`; a transaction balances when debits equal credits. `backend/migrations/commodity_seed.py` is a frozen copy of the ISO list that only the early migrations use; the single-currency migration refuses (changing nothing) when somebody recorded assets of their own, prices, more than one currency or a conversion, and **cannot be undone** (restore a backup instead).

## The four account types (2026-11-22)

finode counts **cash flow, not net worth**. Every account a person adds is one of **four types**, the built-in groups under Assets and Liabilities (`accounts.system_key`; `services/account_types.py` `TYPE_KEYS`, `TYPE_NAMES`): **Bank Account** (`assets.bank`), **Cash** (`assets.cash`), **Credit Card** (`liabilities.cards`) and **Prepaid Wallet** (`assets.wallet`: a meal card, FASTag, a gift card, a UPI or app wallet). An account sits directly under its type (root › type › account: nothing deeper, no account inside another) and **is part of the budget because of its type** (`account_types.in_budget`; the budget, Coming up, people's settlements and the simple form read it, never a flag). There is no account outside the budget, no group of one's own, and no investment or loan account: a SIP, an EMI or a deposit is spending in a category, money borrowed into the bank is income under **Borrowed**, an investment sold is income under **Redeemed**. People's "Due from X" / "Due to X" are the only accounts outside the types (straight under Assets and Liabilities, made by `AccountService.create_contact_account`).

- **Making one:** `AccountCreate.type` (one of the four keys) replaces `parent_id` and `on_budget`; `AccountService.create` puts it under that type's group. `AccountUpdate` changes the name, the note, the balance, the pin and a card's bill days: **an account keeps its type** (a `parent_id` or `on_budget` sent by an old client is ignored). Merging needs the same root (an asset into an asset).
- **The types themselves** cannot be renamed, moved, closed or deleted (`_refuse_fixed`); anyone missing one gets it (`_ensure_roots` makes the roots and the four types). `AccountRead.type` names an account's type (null for a root, a type, Opening Balances or a person's account).
- **Order:** each person orders the four types (`profiles.account_type_order`, migration `e8a0c2d4f6b9`, starting Bank Account, Cash, Credit Card, Prepaid Wallet; `ProfileUpdate.account_type_order` must name each once; `AccountService.type_order()`). The Accounts page's rows, the account form's switcher, the pickers' headings and the assistants' `list_accounts` follow it; Settings › Order of account types moves them. Accounts inside a type stay in name order (ordering single accounts stays removed).
- **Books from before the types** (Investments and Loans groups, groups of one's own, accounts taken out of the budget) are converted by `services/cash_flow.py`: `CashFlowConversion.plan(off_budget_ids, strict, retire_ids, types)` works out every change and makes none; `apply(plan)` carries it out in one commit. Investment and loan accounts are retired: a payment into one posts to Expenses with its category (or one named after the account), money out of one to Income under Borrowed or Redeemed; an entry that touched no budget account and no person (an opening balance of a loan, a fund's value update) is deleted. A person's own groups go and their accounts move under a type by root (Assets: Bank Account, Liabilities: Credit Card) unless a type is chosen. Every kept balance stays as it was on every day and the books still balance. **Strict** (the command `python -m finode.commands.cash_flow --user <id>`, a dry run unless `--apply --backup <file>`; `--retire PATH`, `--as PATH=TYPE`) leaves undecided accounts and entries to the person; **lenient** (every restore of an older backup) decides by those rules. The owner's books were converted on 2026-11-22.

## Naming (2026-10-31)

One convention everywhere (database, code, JSON API, URLs, assistants' output): **a table's primary key is `id`; a column or field that points at another table is `<entity>_id`** (`account_id`, `transaction_id`, `category_id`, `recurring_id`, `from_account_id`, `parent_id`, `related_id`); **the owner is `user_id`**. Path parameters and Python variables are named for what they are (`{account_id}`, `{transaction_id}`, `{token_id}`, `{grant_id}`), never a short code. Migration `b4d6f8a0c2e5` renamed the columns (only names changed; it can be undone); the plan and the table-by-table list are in that migration and in git history (`docs/developer/naming-plan.md`, removed once built). The backup file (version 5) keeps its own readable keys (`account`, `category`) on purpose; a new table or field follows the convention above.

## Queries per page

The database is hosted (about 16 ms a round trip), so **a page must not query once per account or once per row**: that made the new-transaction page take 3.8 s (218 queries) until balances were computed from one query. Rules: list balances from `AccountService._postings_by_account` (one query for every posting, `list()` passes it to `_to_read`), lists of transactions load postings with `TransactionRepository.postings_for_transactions` and transactions with `read_many`, never `read(transaction_id)` or `postings(transaction_id)` in a loop. **The session remembers repeated reads** (`repositories/cache.py`, `remembered`): the account list, the profile, the budget plan, and postings are loaded once per request however many services ask, and forgotten on any write (flush, commit, rollback, a non-SELECT statement) and while the session holds unwritten changes, so a read never shows what was true before a write in the same session. Its results are shared: copy a list before sorting it in place. New repository reads that several services repeat belong there; a new write path needs nothing (flush and commit are hooked). In the test suite the shared session forgets at the start of each request (`conftest.client`, `backend/tests/e2e/conftest.py`), as each production request has its own. A transaction's postings are checked against one account list, never one query per posting. **Entries are written together**: every path that records entries goes through `TransactionRepository.write` (`create` for one, `create_many` for a batch, an import or a restore), which adds the entries, their postings and tags and their lines' categories in a few statements however many there are; after the commit, build the answer from one fresh read (`read_many`) rather than refreshing each entry. The assistants' tools build the account and category index once per call, not once per line. The API's JSON is gzip-compressed (`GZipMiddleware`, which leaves `/mcp`'s event stream alone); nginx compresses the app's files. The budget reads the ledger through `TransactionRepository.posting_rows(date_to)` (postings joined to their date, no payees or notes, one query) rather than every transaction and every posting, and `ReportService.summary` reads income and expense postings in one query (2026-10-25). `backend/tests/guards/test_query_counts.py` counts the statements of the main pages with small and larger books, fails when the count grows with the data and holds each page under a ceiling (`CEILING`: lower it when a page gets cheaper, raise it only with a reason); `backend/tests/guards/test_read_memory.py` guards the memory. To measure on real data without touching production: restore the latest dump into a scratch Postgres, point `FINODE_DATABASE_URL` at it and count statements with an SQLAlchemy `before_cursor_execute` listener.

## What day it is

Never call `date.today()`: use `clock.local_today()` (and `local_now()`, `local_midnight_utc()` for the per-day limit). `FINODE_TIMEZONE` (an IANA name such as `Asia/Kolkata`, validated at start-up) is the zone "today" is read in for the whole installation, so entries, the recurring runner, the budget's current month and "Today" in lists follow the people's clock and not the server's; unset, the server's own clock is used. Timestamps stay in UTC. It is per installation, not per person: a person in another zone would need a profile column and the recurring runner would need each rule's owner's zone. Dependency `tzdata` is there so the slim Docker image has zone data.

## Recent and ordered accounts

**Order (2026-10-25):** accounts are listed alphabetically within their type, the types in the person's order (above; `AccountService.order_key`), by the accounts page, the pickers and the budget's lines. There is no Move up/down for single accounts and no stored order: `accounts.position` was dropped (migration `b2d4f6a8c0e3`; older backups' `position` is read and ignored). `accounts.pinned` was dropped earlier (`b6d8f0a2c4e7`) and came back as a different feature on 2026-11-10 (below). The five built-in groups of 2026-10-21 (Bank Accounts, Cash, Investments, Credit Cards, Loans) and the groups a person could make (2026-11-10) are history: see "The four account types" and [removed.md](removed.md).

### Pinned accounts (2026-11-10)

`accounts.pinned` (migration `d7e9a1c3b5f8`, false by default) lists an account again in a **Pinned** row at the top of the Accounts page; it changes no balance, budget or entry. Only an open account of one of the four types can be pinned (not a type itself, a root, a contact's account or Opening Balances) (`AccountService._check_pin`, a 400 otherwise); taking a pin off is always allowed, and closing an account keeps its flag (the Pinned row hides closed accounts, so reopening brings it back). There is no order of its own: the row follows the order of the rows below it (no Move up/down). It is set by `PATCH /api/accounts/{account_id}` (`pinned`), the assistants' `update_account` (`pinned`; `list_accounts` shows `"pinned": true`) and the account page's menu (`POST /accounts/{account_id}/pin` and `/unpin`). The backup carries it (files from before may leave it out). The first version of this column (dropped by `b6d8f0a2c4e7`) kept no data; the old pins are gone.

## A card's bill (2026-11-01, `feature/card-bills`)

A **Credit Card** may carry a **statement day** and a **due day** (`accounts.statement_day`, `due_day`, 1 to 31, both or neither; migration `d8f0b2c4e6a9` with CHECKs; `AccountBase`/`AccountUpdate`, the account form (asked only for a Credit Card), backup (`BackupAccount`, still version 5), `update_account`/`create_account` tools). `services/cards.py` is the pure calendar (`last_statement`, `next_statement`, `due_date`: day 31 is the last day of a short month; a due day not later than the statement day falls next month). `AccountService.bill(account_id, today)` (`CardBill` in `schemas/account.py`; `GET /api/accounts/{account_id}/bill`, the tool `get_card_bill`) works the bill out from the account's postings (`TransactionRepository.posting_facts`): `statement_balance` = owed at the end of the latest statement day, `paid_since` = debits after it up to today, `spent_since` = credits after it, `bill` = statement less paid, never below zero, `owed_total` = owed today; entries dated ahead are not counted; nothing is stored. The card's screen shows it under the balance (`features/accounts/CardBill.tsx`: Due in N days in amber up to 5 days, Overdue in red, Paid, Nothing due; "Add the days" while unset) with **Pay bill** → `/transactions/new?pay=<account_id>&amount=<bill>&back=…` (the card is the To account, kind Transfer, the amount the total; **the account paid from is left empty**, nothing is filled in for the person). **The bell lists a bill due within `DUE_SOON_DAYS` (5) days or overdue (`TodoService`, `TodoRead.card_bills`, 2026-11-01).** Not built, and the owner does not want them now: recording the bank's statement and the difference, an assistant that matches a statement, autopay confirmation; a "set aside for card bills" line on Budgets is for later. Tests: `backend/tests/ledger/test_card_bills.py`, `backend/tests/migrations/test_migration_card_bill_days.py`, `backend/tests/e2e/test_accounts.py`.

## Posting dates, rounded bills and the rows of the Add screen (2026-11-01, `feature/posting-date`)

**A line may carry a posting date** (`postings.posted_on`, migration `e1a3c5b7d9f2`; `PostingCreate.posted_on`, `PostingRead`, the backup (`BackupPosting.posted_on`, still version 5), the journal (`; posted: 2026-10-18` on a posting, `LedgerPosting.posted`), the assistants' `PostingIn.posted_on` and `_transaction` output, `label_payment`, `preview_update`): the day the account posts the line when that is not the entry's date (a card billing a purchase in a later statement: the owner's IGST lines). Never before the entry's date (`TransactionService._resolve(..., on=)`, and `_check_update` when only the date moves; the form puts a line back on the entry's day when the entry's date moves past it). **Only a card's bill reads it** (`AccountService.bill`: `posted_on or date`); balances, the budget, lists and reports keep using the entry's date. It is available on every account (the row's settings sheet shows the Date for any account, not for categories or in the recurring form), the account page shows "Posts 18 Oct" on a line that differs (`RegisterEntry.posted_on`) and the details sheet "posts 18 Oct" beside the account.

**A card's bill is rounded by the card's rule** (`accounts.bill_rounding` `none|nearest|up`, a CHECK; `BillRounding` in `schemas/account.py`; a select "Round the bill" on the account form; `update_account`/`create_account` take it; backup carry it). `cards.round_bill` rounds the statement balance to a whole unit (halves up for `nearest`); `CardBill` has `statement_balance` (exact), `statement_due` (rounded), `rounded_by` and `bill = max(0, statement_due - paid_since)`, so paying the rounded figure settles the bill and the paise left carry into the next statement. The card page shows a "Rounded" row when the rule changed the figure.

## Recurring transactions

A rule (`recurring_transactions`, `backend/finode/models/recurring.py`) is a transaction on a schedule, in one of two shapes: **simple** (from/to account and amount) or **split** (`recurring_postings` rows, like a transaction's postings ; the simple columns are then empty). The app's form is the Add screen's rows and saves through `POST /api/recurring/form` / `PUT /api/recurring/{recurring_id}/form` (`services/recurring_form.py`: one account on each side with the same amount is a simple rule, anything else a split); the API also accepts either shape directly (`postings`, never mixed with from/to/amount). Both records go through `RecurringService._transaction`. Other fields: payee, note, `frequency` (daily/weekly/monthly/yearly) with `every` N, `start_date`, optional `end_date`, `next_date`, `last_date`, `active` and `last_error`. `services/schedule.py` is the pure date arithmetic (occurrence n = start plus n x every units, anchored to the start so a monthly rule on the 31st falls on the last day of short months). `RecurringService` (`services/recurring.py`) validates a rule with the same checks as recording it (`TransactionService.validate`), and `process_due()` records every occurrence on or before today through `TransactionService.create(..., recurring=(recurring_id, date))`, with `created_via="recurring"`. Each occurrence is recorded **once**: `transactions` has a unique index on `(recurring_id, recurring_date)`, so several workers or repeated visits are safe. Due occurrences are recorded in three places: when Home, the Transactions list or Recurring is read (`RecurringService.catch_up`, which never stops the screen; also when rules are listed or made through the JSON API), and by `backend/finode/recurring_runner.py`, a background loop started in `main.lifespan` in every worker (`settings.recurring_interval_minutes`, default 15, 0 turns it off; the first run waits a minute). A rule that cannot be recorded (an account that can no longer be posted to) keeps its `last_error` and retries on the next run. **Skipping one occurrence** (`RecurringService.skip_next`, `POST /api/recurring/{recurring_id}/skip`, the "Skip <date>" button on the rule's screen, MCP `skip_recurring_occurrence`): nothing is recorded for the next occurrence and the rule moves on to the one after; the skipped day is kept in `skipped_date` (not `last_date`, which stays "last recorded"), so editing the rule continues after whichever of the two is later and never revives it; only a running rule can skip, it clears a stuck `last_error`, and skipping the last occurrence before `end_date` ends the rule. Pausing then resuming skips what fell due meanwhile; editing continues after the last recorded or skipped day; deleting keeps the recorded transactions (their link is cleared); an account used by a rule cannot be deleted. The app: `/recurring` (list, new, edit with pause/resume/delete); JSON API: `/api/recurring`; MCP: `list_recurring`, `create_recurring` (simple, or `postings` for a split), `stop_recurring`, `skip_recurring_occurrence`. "Today" follows `FINODE_TIMEZONE`.

**Related entries (2026-10-24).** `transactions.related_id` (migration `e7b9d1f3a5c8`, self-referencing, nullable, indexed) links an entry to an earlier one: a refund, reversal or cash-back, with no relation type yet (neutral wording: "Related to", "Related"). It is a link only: no amounts, balances, budget or reports read it. `TransactionCreate.related_id`, `TransactionUpdate.related_id` (null removes, leaving it out keeps) and `TransactionRead.related_id` carry it through the JSON API; `TransactionService._check_related` refuses an id that is not the person's own, an entry related to itself and a circle (`InvalidPostingError`, so a 400); `TransactionRepository.delete` clears what pointed at the deleted entry; `TransactionService.related(transaction_id)` lists the entries pointing at one. Deleting an entry unlinks what pointed at it. The backup carries `related_id` and a restore links last, mapped to the new ids. The app: the details sheet has **Related** (`/transactions/new?related=<transaction_id>`: a blank new entry that only carries the link, nothing copied from the original, 2026-10-24) and a "Related to" / "Related · N" list of rows that open the other entry's sheet in place (`related_info`); the Add screen has a chip "Related to <payee · date · amount>" with ✕ and, with no link, a chip "Related" (link glyph, next to the date chip) that opens our own picker (`features/entry/RelatedPicker.tsx`, `GET /api/views/related-entries`: the 30 newest entries up to today without Opening balance and Balance adjustment, `q` searches like the list's text search, `exclude` leaves one out). `/api/entries` takes `related_id` (null clears it). **In the lists (2026-11-01) only the linked entry (the one that holds `related_id`) is marked, never the original:** after its payee a grey pill (`features/transactions/RelatedPill.tsx`) with the link glyph and the original's date and amount; the payee gives way first (ellipsis), the pill stays whole; tapping the pill opens the original's sheet, tapping the row opens its own. The date and amount come from `RelatedRef` (`schemas/transaction.py`), loaded in two queries by `TransactionRepository.related_refs` (none when nothing is related): `list_rows` in `services/transaction_rows.py` for Home and the Transactions list, `RegisterEntry.related` for an account's and a category's page (also in the JSON registers). The mock-ups chose this over grouping under the original, which would have reordered days. The assistants set it with `related_to` on `record_transaction`, `record_split` and `update_transaction`, and `get_transaction` lists the entries pointing at one (2026-10-25).

**Tags are their own thing, apart from the note (2026-10-26).** Before this a tag was a `#word` in the note (`backend/finode/tags.py`, nothing stored). Now `tags` (`id`, `user_id`, `name`: lower case, 1 to 30 characters of letters, digits, `-`, `_`, at least one letter, unique per person) and `transaction_tags` (migration `a2c4e6f8b1d3`, which moved every existing tag out of the notes; its downgrade appends them back) hold them. **A tag exists only while an entry carries it** (`TransactionRepository.set_tags` drops unused ones). An entry has up to 10 tags (`MAX_TAGS_PER_ENTRY`), a person up to `FINODE_MAX_TAGS` (200, `TransactionService._check_tags`). `backend/finode/tags.py`: `clean_name`/`clean_names` make the one form (no `#`, lower case); `tags_in`, `without_tags`, `split_note` remain only for the migration and for backups before version 3. Schemas: `TransactionCreate.tags`, `TransactionUpdate.tags` (`None` keeps, `[]` clears), `TransactionRead.tags`; `_to_read(..., tags)`: every list loads the tags of its rows with one query (`tag_map`; Home and Transactions gained that one query, ceilings 13 and 11). Renaming, merging and deleting a tag (`rename_tag`: into an existing tag it merges, `merge_tags`, `delete_tag`) change the entries' tags only. **The app:** the note is plain; a `#` button inside it opens our own tags sheet (`components/lines/NoteAndTags.tsx`: search, tick, "＋ Create “#word”", the tags in use from `GET /api/tags/`), and the chosen tags sit as one row of soft `#tag` chips under the note (one row, clipped with a fade; no room while empty); tags are shown with a `#` everywhere but stored without it, and `/api/entries` takes `tags`. Rows show only the note (no tags, at the owner's request 2026-10-26); the details sheet has a Tags row of links to Transactions filtered by the tag in the entry's month; the Transactions view takes `tag`, and the Filter sheet lists the tags; with a tag set the line under the title adds the match up. **Settings › Your data › Tags** (`/tags`, `features/tags`): the list, and per tag Rename, Merge into…, Delete. **API:** `GET /api/tags/`, `PATCH /api/tags/{name}`, `DELETE /api/tags/{name}`; the list takes `tag`. **Assistants:** `tags` on `record_transaction`, `record_split`, `record_transactions` and `update_transaction` (which also takes `add_tags` / `remove_tags`); a `#word` in a note written by an assistant is text and the reply carries a `notice`; `rename_tag`, `merge_tags`, `delete_tag` are `MANAGE_TOOLS` (the "manage" level now covers accounts and tags; `NO_MANAGE_MESSAGE` says so). **Backup** version 3 carries each entry's `tags`; a file before version 3 has its notes' `#words` moved into tags on restore (`split_note`);

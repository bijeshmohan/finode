# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Documentation

`docs/` holds the user guide, the architecture (with Mermaid diagrams) and the developer docs (`docs/index.md` is the entry). This file stays the dense rulebook for assistants; when behaviour or a rule changes, update the matching page in `docs/` as well.

## Commands

- Apply migrations: `uv run alembic upgrade head` (run before first boot and after pulling schema changes)
- Run dev server: `uv run fastapi dev` (auto-reload, http://localhost:8000)
- Run prod-ish: `uv run fastapi run`
- Run tests: `uv run pytest`
- Run the browser tests: `scripts/browser-tests.sh` (needs Docker: the browser runs in Playwright's container, the tests and the app on this machine); `FINODE_BROWSER=webkit scripts/browser-tests.sh` for WebKit, the closest to iOS Safari. Where Playwright's own browsers work, `uv run playwright install chromium` then `uv run pytest tests/browser`. A plain `uv run pytest` skips them when there is no browser. `tests/browser/` starts the real app on a free port with a fresh in-memory database and drives it like a user; add a test there for any behaviour that lives in `app.js` or needs a real browser (the unit tests only see server-rendered HTML). Keep the playwright version in `pyproject.toml` and `scripts/browser-tests.sh` the same.
- Generate a migration: `uv run alembic revision --autogenerate -m "description"` (always review before applying)
- Add a dependency: `uv add <pkg>` (do not edit `pyproject.toml` by hand)
- Deploy with Docker: `docker compose up -d --build` (runs migrations via the one-off `migrate` service, then the app behind Traefik; needs `.env` with `APP_DOMAIN`)
- Build the image only: `docker build -t finode .`

Python 3.14+ is required (see `pyproject.toml`). No linter or formatter is configured — do not invent commands for these.

## Architecture

All application code lives under `app/`. The core domain is a double-entry
ledger with accounts and journal entries:

- `app/models/` — SQLModel ORM tables (`table=True`). Source of truth for the schema is the model + Alembic migrations together.
- `app/schemas/` — Pydantic request/response models. Each entity exposes `*Base`, `*Create`, `*Read`, `*Update`.
- `app/repositories/` — tenant-scoped persistence classes over a `Session`.
- `app/services/` — business logic and cross-entity orchestration. Journal
  balancing and account balance derivation live here.
- `app/routers/` — FastAPI `APIRouter`s. Convert `None` from repositories/services into `HTTPException(404)`. Routers never touch the DB directly — always go through a repository or service.
- `app/routers/web/` — the HTML UI at the site root (`/`, `/accounts`, `/login`…), rendered with Jinja2 (`app/templates/`) and enhanced with vendored htmx (`app/static/`). It calls the same services as the JSON API and must not duplicate ledger rules; view-model helpers (account tree, posting pickers) live in the web routers.

**The JSON API (`/api`) is small on purpose**: accounts (list, create, get, update, delete, close), transactions (list, create, get, update, delete), the profile, recurring rules (CRUD and skip), the budget (read, assign, targets), the trial balance, backup, restore, export and import. Everything else (reopening, ordering, restoring deleted things, copying or funding a budget, a register, the reports) is the web app and the MCP tools; tests reach that through the services (`tests/svc.py`) or the web routes. A new route is for the web UI or the assistants first.

`app/main.py` wires the routers: the JSON API is mounted under `/api` (so `/accounts` is the page and `/api/accounts/` the API), `/mcp` and `/static` stay at the root, and the old `/...` paths redirect (301) to their new place. The web login cookie path is `/`. Schema is managed by Alembic — `app/main.py` does *not* run `SQLModel.metadata.create_all` at startup. Run `uv run alembic upgrade head` to bring the DB to the latest schema. The dev DB is `finode.db` (SQLite, gitignored).

`app/config.py` exposes a `settings` instance (pydantic-settings) reading `FINODE_*` env vars and an optional `.env` file (other keys are ignored because `.env` is shared with docker compose). Current settings: `database_url`, `database_echo`, `supabase_url`, `supabase_audience`, `supabase_anon_key`, `cookie_secure`, `mcp_rate_limit`, `recurring_interval_minutes`, `supabase_service_role_key`, `signup_code`, `api_docs`. Add new configuration here rather than hardcoding constants.

`app/dependencies.py` builds the engine from `settings` and exposes `DBSession = Annotated[Session, Depends(get_db_session)]`. Route handlers should type the session parameter as `DBSession` directly rather than re-declaring `Depends(...)`.

All imports within `app/` use relative imports (e.g. `from ..models.account import Account`). The FastAPI CLI entrypoint is configured in `pyproject.toml` under `[tool.fastapi]` as `entrypoint = "app.main:app"`.

### Web UI

There is no JavaScript build step; do not add one. Templates extend `base.html`; `partials/` holds fragments returned to htmx. Mutating forms use `hx-post` (htmx 2 sends `DELETE` parameters in the URL, so use `POST` routes such as `/{id}/delete`). Handlers answer success with `htmx_redirect(location, flash=...)` and failures with a 4xx plus `HX-Retarget` pointing at an error element, via `routers/web/utils.py`; `static/app.js` lets htmx swap those 4xx responses.

UI conventions (keep pages working on phones first):
- Layout: `base.html` renders a slim top bar (the wordmark and an avatar that leads to Settings) and a bottom tab bar of four tabs (Home, Budget, Accounts, Categories) with a floating "+" on phones (Transactions has no tab and no icon: it is reached from "View all" on Home and the sidebar); from 60rem up a fixed sidebar (new-transaction button, those links plus Transactions, Settings at the bottom) replaces the top bar, tab bar and "+", and the page is one calm column. Pass `active` for the current section and `hide_fab=True` on form pages (it hides the "+" and the sidebar's button). Sign-out lives at the bottom of the profile page, which is reached from Settings. The look is set by the tokens at the top of `style.css` (warm neutral greys, ink-coloured actions, green and red only for money in and out, light and dark) and the self-hosted Figtree font (`static/fonts`, `@font-face` inline in `base.html` with the hashed URL and a preload); keep text inputs at 16px or more so iOS does not zoom, and prefer our own chips and sheets to native pickers so iOS and Android look the same. The target design is the mockup the owner approved (calm, minimal, quick entry): Home with one number and the transaction rows without card borders (new transactions start from the floating "+" on phones and the sidebar button on wide screens).
- The accounts page (`accounts.html`, `page_blocks` and `mark_closed` in `routers/web/accounts.py`, the `accountsPage` block in `app.js`): **nothing folds** except Equity (a native `<details>`). Accounts go two levels deep, so a group is a heading (name, subtotal, links to its own page) with its accounts always open in a tile under it; plain accounts directly under a type share one tile without a heading; rows are a round initial, the name and the balance. "Recently used" cards (the last five accounts used by hand, swipeable) sit above the types and the search hides them. A search box filters by path (a matching group brings its accounts). **Every open account is listed**, used or not (nothing is hidden for having no entries or a zero balance); only **closed** ones wait behind one "Load more" button (it shows them and goes away; they carry a badge). The page has no note under the list.
- **Closing accounts** (`AccountService.close` / `reopen`, `accounts.closed_on`; `POST /api/accounts/{aid}/close`, `POST /accounts/{aid}/reopen`, the Close/Reopen card on the account page): a closed account (and everything inside it) keeps its history but can't be posted to (`TransactionService._resolve`; an entry that already uses it stays editable), can't get sub-accounts or a balance change, and leaves the pickers (`posting_groups`, keeping what an entry being edited uses), the accounts list (behind "Load more"), the budget once a closed category has nothing left in the month, and the assistants' `list_accounts` (`include_closed`). Closing is refused while anything inside holds a balance (now or in a future-dated entry) or a running recurring rule uses it; it clears the category's targets and payment-category links. Reopening reopens the account, what is inside it and the groups above it. **For a category (Expenses/Income) the word is Delete**: the menu on a category's page and the Edit page's button call `POST /accounts/{aid}/delete`, which removes an unused category for good and, when it has entries, subcategories or is in a rule, closes it instead (`category-deleted`; it leaves the lists and pickers, stays in the months where it has amounts, and "Restore category" reopens it); a category's balance is spending, so closing one never waits for it to be empty. Accounts (Assets/Liabilities) keep Close and Reopen, behind Advanced.
- Lists use `partials/transaction_list.html` (rows from `transactions.to_row`, grouped by day with the `friendly_date` filter); format amounts with the `money` filter. Avoid tables — they overflow on phones.
- Rows are links to a detail or edit page; destructive actions live on that page, not on list rows.
- Forms that can be opened from several places accept a `back` path and return there after saving; always pass it through `safe_back`, which only allows local paths of the web UI (not `/api`, `/mcp`, `/static`…).
- Confirm actions with a flash: add the message key to `MESSAGES` in `app/flash.py` and pass it to `htmx_redirect`.
- Account pickers on the transaction forms use `account_options(groups, selected, allow_new=True)` and carry `data-account-select`; `app.js` opens the `<dialog id="quick-account">` sheet (`/accounts/quick`) when "+ New account…" is chosen, then refreshes every picker from `/accounts/options` on the `account-added` event. Restore pickers synchronously (`cancel` event, cancel buttons), never from the async `close` event alone.
- Icons come from the `icon()` macro in `partials/icons.html`; styles use the CSS variables at the top of `static/style.css` (both light and dark themes).

`app/web_auth.py` signs users in through Supabase's password grant and keeps the tokens in `HttpOnly` cookies. `web_login_required` verifies the cookie (refreshing it when expired) and stores the token in `request.state`, which `require_authenticated_user` accepts in addition to a bearer header, so repositories stay tenant-scoped. The JSON API never reads cookies. Sign-up is invite-only: `app/signup.py` checks the invite code (constant time) and creates pre-confirmed users through Supabase's admin API with the service key, which must stay server-side — never render it, log it or send it to the browser. `settings.signup_enabled` gates the routes (404 otherwise). In tests, `tests/conftest.py` overrides both dependencies; use a client without the `web_login_required` override (see `tests/test_web_auth.py`) to test real authentication.

### What an amount field accepts

Every `input[inputmode="decimal"]` (the transaction form, the budget's sheet, move and target, account balances) is cleaned as it is typed or pasted (`cleanAmount` at the top of `app.js`, a capturing `input` listener so the other handlers read the clean value): digits, commas to group them, **one** decimal point (a second one is ignored, so `42.00.00` becomes `42.0000`, which is 42) and a minus sign only first; letters and anything else are dropped and the cursor stays where it was. The number of decimals is still the server's job (`check_places`: it normalizes first, so trailing zeros pass and `42.005` in rupees is refused with a message), because the page does not know the currency's places. `parse_amount` refuses anything left that is not a number.

### The amount field's focus

On a new entry the amount carries `data-autofocus` (not `autofocus`): `app.js` focuses it only when the device has a mouse (`(hover: hover) and (pointer: fine)`). On a phone nothing is focused, because a script cannot open the keyboard: the grey 0.00 stays visible until the person taps the amount, which hides it (`:focus::placeholder`), shows the cursor and opens the keyboard. Tapping a payee chip still focuses the amount (a real tap, so the keyboard opens).

### Lakhs and crores

For INR the whole part of an amount is grouped the Indian way (`12,34,567.00`: the last three digits, then pairs), every other currency in thousands (`1,234,567.00`). `templating.money` follows the person's currency without being told: the `protected` web router loads it for every page (`dependencies.load_currency` puts it in `request.state.currency`), and `templating.TemplateResponse` is wrapped to set a context variable (`_grouping`) while the page renders, so the 60 `|money` call sites did not change. Python code that writes an amount into a string outside a template passes the style (`money(value, grouping_for(code))`, as the budget's hints do). `<html data-grouping="indian|western">` tells `app.js` (`groupDigits`, used by the allocation status under the form's From/To rows). Amounts under one lakh read the same either way (99,999.00). Only the rupee is grouped this way; PKR, BDT and others stay in thousands unless asked.

### The rupee sign and what was added automatically

For INR the unit is the rupee sign, **in front** (`templating.symbol` / `amount`; the `figure` macro in `partials/money.html` for large figures: Home, Budget's Ready to assign; the Add screen's amount has it in front of the digits, which is as wide as what is typed: `--n` set in `recomputeTxn`). Other currencies keep their code after the amount (the person's one currency, see "One currency"; the amounts in lists carry no unit at all). Figtree's rupee glyph is not in the Latin subset we self-host, so `static/fonts/figtree-rupee.woff2` (about 1 KB, only U+20B9, cut from Google's latin-ext file with fontTools, OFL) carries it, declared in `base.html` with `unicode-range:U+20B9`; without it each phone would draw its own sign. What an assistant or a recurring rule added is **blue** (`--auto`, light and dark): the "Recurring" / "Added by Claude" line under a row (`.tx-via`) and the "Added" and "Repeats" facts in the details sheet (`dd.auto`).

### Signs and the pace tick

Amounts in transaction lists, the details sheet and an account's activity show **no minus on ordinary spending** (the default, so a long list is not a column of signs): income is `+` and green (`.tx-amount.income`), transfers plain. A real negative (an overdrawn account, an overspent category's "left", a debt) keeps its `−` and red; the `money` filter still writes a true minus sign. Every progress bar (Home's `.glance-bar`, the budget's `.crow .bar`, the Categories `.sharebar`) is **6 px thick**, from the one token `--bar-h` at the top of `style.css` (the tick is `--bar-h` + 9 px tall): change it there, never per bar. Bars of the current month carry a **tick (a short vertical line) showing how far through the month today is** (`clock.month_progress`, `.pace` inside `.glance-bar` on Home and `.bar` on the budget; `pace` is None for other months, which have no today): a fill ahead of the tick is spending faster than the month passes. **Green and "+" mean money coming in**, which on an account's own page (`_is_inflow` in `routers/web/accounts.py`, offered to the template as `is_inflow`; also used by the upcoming card) is what **raises an asset account** and a **payment into a liability** (a card or loan: it lowers what you owe). A charge on a card is plain, with no sign; the running balance beside each row shows which way it went. Income categories are green, Expenses plain.

### The "i" beside Home's and Budget's figure

A round `i` (`.calc-info`) sits beside the label of **Left to spend** (Home) and **Ready to assign** (Budget) and opens, in place under the figure, the sum behind it with the person's own numbers (`partials/calc_info.html`: `calc_button`, `calc_panel`; shown by CSS `:has(.calc-info[open])`, no script). Home: carried in from earlier months (`glance.carried` = available - assigned + spent) + assigned this month - spent = left. Budget: money in the accounts - set aside for card bills - left in the categories - assigned to later months = ready to assign (`BudgetRead`; the panel shows the true figure, so a negative one reads as it is, while the headline stays at zero). Every row shows even at zero so the column always adds up; a negative amount flips its sign instead of showing a minus. If the budget's arithmetic changes, change the rows here and the two tests that read them.

### Recently deleted

`/transactions/deleted` (the bin icon beside Recurring on the Transactions page; `routers/web/transactions.py`, `transactions_deleted.html`) lists what was deleted, newest deletion first, with **Restore** on each (`POST /transactions/deleted/{hid}/restore`; `hid` is the deletion's id, from `TransactionService.deleted()`). It reads the append-only `transaction_history` (nothing new is stored): `TransactionService.restorable()` keeps the newest deletion of each entry that is not back, `restore()` recreates it **with its old id** (so its history reads created, deleted, created and it leaves the list), validated like any entry (a locked period, a closed or deleted account, the limits refuse it with the reason). Only the latest deletion of an entry can be restored. It comes back as an ordinary entry: the link to a recurring rule is not restored (the occurrence's date is not in the snapshot, and the rule could otherwise record the day twice) and the "added by" origin becomes the restorer's. `tests/test_isolation.py` knows the `hid` parameter.

**Accounts and categories** have the same (`/accounts/deleted`, `/categories/deleted`, the bin icon in each page's header; three chips link the three pages). Two kinds of rows: **closed** ones (`AccountService.closed()`: the outermost of each closed branch; a category with a history is closed when "deleted", an account when closed) restored with the existing `POST /accounts/{aid}/reopen`, and **deleted for good** ones (only an unused account or category can be: no entries, sub-accounts or rules) restored with `POST /accounts/deleted/{did}/restore` (`AccountService.restorable()` lists them). `AccountService.delete` writes an `account_deletions` row first (migration `c8f0b2d4e6a1`, append-only, no foreign key to the account; erased with the books like every table with a `user` column, not in the backup): the name, parent, note, budget flag, payment category, place, the amounts planned for it, its target and the accounts that budgeted their payments under it. `restore_deleted` recreates it **with its old id** and all of that, refusing with a reason when the parent is gone or closed, the name is taken in that parent, the depth or the account limit would be broken, or it was already restored or deleted again later. The audit knows the `did` parameter.

### Offline, failed saves and loading

`base.html` carries one `#net-banner` (hidden) and a `.loadbar`; the last block of `app.js` drives them. Offline (`navigator.onLine`) shows "You're offline…" until the connection is back; a request that cannot reach the server (`htmx:sendError`), times out or answers 5xx shows a message that says **the entry is still on the page** (forms are never cleared on failure, and 4xx validation messages still swap in as before); a later successful request clears an error. The bar shows while an htmx request or a page load is under way, and a form being sent cannot be sent twice (`form.htmx-request` disables its buttons). There is **no offline queue**: nothing is saved until the connection is back (browser tests in `tests/browser/test_states.py`, run in Chromium and WebKit). Empty states are a short sentence and one next step, without a box.

### Bento tiles

Rows are grouped into soft rounded tiles (`--surface` with a `--tile-border` hairline, a hairline between rows inside, a gap between tiles) so groups are easy to tell apart while the page stays minimal: a tile per day in transaction lists (`.tx-day ul.card.list`), per account type and per group on the accounts page, per group of categories on the budget (`.budget-tile`, opened in `budget_body.html` at each top-level group and at the first plain category after one) and per section in Settings (`.tile`). The tile rule is one block at the end of `style.css`; new lists should reuse it rather than draw their own borders.

### Dark mode

Both dark blocks at the top of `style.css` (the automatic `prefers-color-scheme` one and the manual `data-theme="dark"` one) must define the same tokens (a test compares them). Use tokens only, never literal colours (the one exception is the white switch knob, which switches to `--on-accent` when on). Form fields use `--field-border` (stronger than the hairline `--border` in dark so empty fields are visible), the big amount placeholder uses `--faint`, and `favicon.svg` switches between ink and paper with `prefers-color-scheme`. `apple-touch-icon.png` is still the older blue mark.

### The Advanced switch

`profiles.advanced` (migration `e2a4c6e8f1b3`; Settings › Advanced, `POST /settings/advanced`, `PATCH /api/profile/` with `advanced`; carried by the backup) shows or hides the rarely used features, **never touching their data**. Off hides: budget targets and "Assign what is needed" and the week-by-week view (`budget_body.html`), Move up/down and Close account on an account page (a closed account still offers Reopen) (`account.html`), and on the Advanced page the period lock (`advanced.html` lists it dimmed). The JSON API, the assistants' tools and everything already stored keep working (a hidden target still counts in `get_budget`). People who had a profile when the migration ran have it **on**, so nothing disappears on deploy; new profiles start **off** (`repositories/profile.NEW_PROFILE_ADVANCED`, which `tests/conftest.py` switches on so tests see every feature). Read it with `ProfileRepository.advanced()`; any new rarely used feature should hide behind it. The Settings page is a short list (profile header, currency, appearance, backup/export, recurring, AI assistants, Advanced, feedback, sign out); the name and the data pages stay under `/profile`.

### Profile and settings

The web UI keeps two pages apart: **Profile** (`/profile`, person icon) is about the user's account (name, email, AI assistants, export/import, sign out); **Settings** (`/settings`, gear icon in the top bar and the last tab) is about how the application works (currency, appearance, the Advanced switch, links to recurring transactions). Put every new application setting on the Settings page (`routers/web/settings.py`, `settings.html`; forms post to `/settings/...`), not on Profile. Storage is unchanged, described next.

`app/models/profile.py` holds one `profiles` row per user (names, currency) (keyed by the Supabase user id, created lazily by `ProfileRepository.get_or_create`). Per-user details and application settings are **typed columns on that table** — add a setting with a column, a migration and a field on `ProfileUpdate`, not a key-value or JSON store. Supabase `user_metadata` is deliberately not used: users can write it directly and it is copied into every token. `/profile` has an initials avatar header and the name row; `/settings` has collapsible `<details class="setting">` rows (currency, appearance) that `app.js` opens when the URL hash names them; `/profile/data` is export and import. The light/dark override is per browser, kept in the `finode_theme` cookie that `base.html` reads, not a profile column. The JSON API is `/api/profile/`. Email and password stay with Supabase.

### One currency

Everyone keeps their whole ledger in **one currency**: `profiles.currency` (an ISO 4217 code, INR for new people; migration `f4b6d8a0c2e5`), chosen in Settings › Currency (`POST /settings/currency`, `PATCH /api/profile/` with `default_currency`, the field name kept for API clients). Changing it **relabels, never converts**: every stored amount stays as it is (the page says so). There are no other currencies, no assets of one's own (shares, funds, coins), no prices and no conversions; the `commodities` and `prices` tables, `accounts.commodity_id`, `transactions.currency_id` and `postings.value` were dropped. The currency list is `app/currencies.py` (`CURRENCIES`, `find`, each with its decimals and sign); `AccountService.currency()` and `TransactionService.currency()` read it for the person, and `check_places` / `TransactionService._resolve` refuse amounts with more decimals than it allows (rupees 2, yen 0, dinars 3). `Amount` columns stay `Numeric(24,8)` (read back without padding zeros: do not format money with `:.2f`, use the `money` filter or `normalize_amount`). A posting is just an `amount`; a transaction balances when debits equal credits. `migrations/commodity_seed.py` is a frozen copy of the ISO list that only the early migrations use; the single-currency migration refuses (changing nothing) when somebody recorded assets of their own, prices, more than one currency or a conversion, and **cannot be undone** (restore a backup instead). Transaction history snapshots written before still carry `currency_id` and a `value` per posting; readers ignore them and `TransactionRepository._comparable` keeps them from counting as a change.


### Import and export

`app/ledger/` reads and writes the plain-text ledger journal format (`parse.py` / `write.py`, no dependency); `app/services/data.py` (`DataService`) maps it to accounts and transactions and also writes a CSV. Exports are always allowed (`/api/export`, `/export`). Import is **only allowed while the user has no transactions**, previews first (`?dry_run=true`, `/import/preview`) and is all-or-nothing in one database transaction. Debit is positive, credit negative; `Assets:Bank:HDFC` maps to the account tree, root names accept aliases (`Asset`, `Revenue`...), `Equity:Opening Balances` maps to the system account. Unsupported input (conversions between currencies, prices, virtual postings, automated/periodic transactions, `include`, balance assignments) is an error with its line number, never silently dropped. Imported postings follow the same rules as the transaction service (no postings to roots, or to Assets/Liabilities/Equity groups); keep `DataService._plan` in step with `GROUP_POSTING_ROOT_NAMES` if that rule changes. Account names cannot contain `:` because it is the ledger path separator.

finode keeps one currency, so the parser reads an amount with an optional label (`INR`, `₹`, `$`) but does not tell labels apart: `DataService._plan` accepts bare amounts and the person's own currency code or sign and refuses any other label with the line number and a pointer to Settings (change the currency first). Conversions (`@` / `@@`) and `P` price lines are errors; `commodity` directives are accepted and ignored. Exports have bare numbers and CSV has six columns (`date, payee, note, account, debit, credit`).

### Full backup and restore

`services/backup.py` (`BackupService`) writes everything a user recorded as one JSON file (`GET /api/backup`, `/backup`; format `finode-backup`, `version` 2, version 1 files are still read, models in `schemas/backup.py`): settings, accounts (with `on_budget`, `closed_on`, `payment_category_id`), transactions with their postings and origin, recurring rules (simple and split) and the budget plan and targets. Left out on purpose: access tokens and connected apps (secrets; set them up again) and the audit history. `restore()` (`POST /api/restore`, `?dry_run=true`, `/restore/preview`, `/restore`) rebuilds a ledger from it, **only into an empty one** (no accounts of the user's own, no transactions, recurring rules or budget), all or nothing in one database transaction, validating the file first (the currency is known, accounts exist, no cycles, every transaction balances) and creating everything with **new ids** (the system roots and Opening Balances map onto the user's own). A version 1 file (from before one currency) restores when everything in it is in the profile's currency; one with assets of its own, prices, another currency or a conversion is refused with a message. The legacy fields (`commodity`, `value`, `currency`, `received_amount`, `commodities`, `prices`) are read but never written (`Field(exclude=True)` in `schemas/backup.py`). `tests/test_backup.py` round-trips a ledger that uses every feature; when you add a model or an account/budget flag, add it to the backup and to that test, or it will silently be missing from backups.

### MCP server (AI assistants)

`app/mcp_server/` serves an MCP server at `/mcp` (Streamable HTTP, **stateless with JSON responses**, so any worker can answer any request) built on the official `mcp` SDK (2.x: `MCPServer`, not `FastMCP`). It is a plain ASGI route added in `app/main.py`, and `main.lifespan` runs the SDK's session managers (`transport.lifespan` builds fresh ones on every start, because tests start the app many times).

- **Auth (phase 1):** personal access tokens (`api_tokens`: only a sha256 of the `fin_…` secret is kept, plus a display prefix, scope `read`/`write`, last used, revoked). Users create and revoke them on `/profile/assistants`; the secret is shown once. `transport.MCPEndpoint` checks the bearer token, applies a per-token per-process rate limit (`settings.mcp_rate_limit` a minute), puts the `TokenOwner` in `context.current_owner` and hands the request to the server for that scope: read-only tokens get a server whose write tools are still listed but only refuse, telling the assistant to ask the user to allow read & write under Profile › AI assistants (`tools._refused`). Tokens only work on `/mcp`, never on the JSON API, and cannot manage tokens. - **OAuth (phase 2, for claude.ai, the Claude mobile app and other connectors):** Supabase's OAuth 2.1 server (Authentication › OAuth Server in the dashboard: enabled, authorization path `/oauth/consent`, dynamic client registration on) registers the apps, runs the sign-in and issues their access tokens; finode never issues tokens. `/.well-known/oauth-protected-resource[/mcp]` (RFC 9728, `transport.protected_resource_metadata`) names Supabase as the authorization server, and every 401 from `/mcp` carries `resource_metadata` in `WWW-Authenticate` so clients can discover it. Supabase redirects the user to `/oauth/consent?authorization_id=…` (`routers/web/oauth.py`, `app/oauth.py` calls `/auth/v1/oauth/authorizations/{id}` and `…/consent` with the user's own session token); the user picks read-only or read & write and the choice is stored in `oauth_grants` (per user and Supabase `client_id`: Supabase has no read/write scope). On `/mcp` a JWT must verify against Supabase's keys **and** carry a `client_id` **and** match a non-revoked grant of that user, which supplies the scope; ordinary sign-in tokens (no `client_id`) are refused there, and conversely an app's token is refused by the JSON API and web UI (`auth.reject_app_token`), so it can never act as a full sign-in. Disconnecting (Profile › AI assistants › Connected apps) revokes the grant and asks Supabase to revoke the app's tokens. The login page carries a `next` only for the consent page (`web_auth.safe_next`).
- **Assistants page UX:** `/profile/assistants` lists apps and tokens together (`partials/connections.html`, with Allow changes / Make read only on each, `…/access` routes, no re-creating needed) above the two ways to connect. `partials/access.html` (`level` macro) spells out each access level and is shared by the token form and the consent page, whose buttons carry the choice (`allow-read`, `allow-write`, `deny`) instead of a radio.
- **Tools** (`tools.py`) call the same services as everything else through `context.services()` (which builds them for the token's user, like `dependencies.py`). They take account paths (`Assets:Bank:HDFC`, a unique end like `HDFC`, or other separators), resolved by `accounts.AccountIndex.find`, which explains ambiguous or unknown names. Amounts go out as strings. Service errors become `ToolError`s with the service's message. Write tools carry MCP annotations (`delete_transaction` is destructive). Assistants can create accounts but never delete or edit them. Keep `INSTRUCTIONS` in step with ledger rules.
- **Origin:** transactions record `created_via`/`updated_via` (`web`, `api`, `import`, `mcp:<token name>`), set by `TransactionService(origin=...)` (`dependencies.get_transaction_service` decides web vs api from the path). The list marks entries made or changed by an assistant; the edit page says who added and last changed it.
- The transaction form (`transaction_form.html`, `partials/txn_row.html`, `recomputeTxn` in `app.js`) is one page: a large **total**, then a **From** section (credit rows) and a **To** section (debit rows), each a list of account + amount rows. Each side starts with one row whose amount is the total, shown grey (a *suggestion*: a real value, class `suggested`, selected on focus so typing replaces it). When the user types a different amount in a row, it becomes theirs (`data-touched`) and a new row appears with the remainder suggested; rows are added until the side adds up and an unused suggestion row is dropped once nothing is left. At the top are the **Expense / Income / Transfer** buttons (Expense is the default; tapping the selected one again selects nothing, which offers every account and is the "other" kind) (`data-kind`, hidden `kind` field, ignored by the server; `KINDS` and `applyKind` in `app.js`): they narrow the account pickers by type (expense: from assets or liabilities to expenses; income: from income to assets or liabilities; transfer: between assets and liabilities; other: everything) by rebuilding the option lists, not hiding options, because iOS ignores hidden options. The server picks the starting kind (`infer_kind` in `routers/web/transactions.py`: expense by default, from the account when opened from one, inferred from the postings when editing, "other" when they fit none); swapping From and To, or creating an account of a type the kind does not offer, switches to "other" (or keeps "transfer"). The form always saves through `/transactions/split` or `/{tid}/edit` (the `total` field is ignored by the server; the older one-from-one-to routes `POST /transactions` and `/{tid}/edit/simple` were removed, `simple_postings` stays for recurring rules and the assistants' `record_transaction`). `services/simple.py` turns from/to/amount into postings for both the web form and `record_transaction`; `ReportService.breakdown` (also `/reports/breakdown`) gives per-account income or expenses.
- Tests talk to `/mcp` over HTTP with the SDK client and an in-process ASGI transport (`tests/mcputil.py`: `make_token`, `running_app`, `mcp_client`, `payload`); tests are `async` with `pytest.mark.anyio`.

### Recurring transactions

A rule (`recurring_transactions`, `app/models/recurring.py`) is a transaction on a schedule, in one of two shapes: **simple** (from/to account and amount) or **split** (`recurring_postings` rows, like a transaction's postings ; the simple columns are then empty). The web form is the transaction form's rows (`partials/txn_rows.html`: total, From and To rows) and saves one account on each side as a simple rule, anything else as a split (`_parse` in `routers/web/recurring.py`); the API accepts either shape (`postings`, never mixed with from/to/amount). Both records go through `RecurringService._transaction`. Other fields: payee, note, `frequency` (daily/weekly/monthly/yearly) with `every` N, `start_date`, optional `end_date`, `next_date`, `last_date`, `active` and `last_error`. `services/schedule.py` is the pure date arithmetic (occurrence n = start plus n x every units, anchored to the start so a monthly rule on the 31st falls on the last day of short months). `RecurringService` (`services/recurring.py`) validates a rule with the same checks as recording it (`TransactionService.validate`), and `process_due()` records every occurrence on or before today through `TransactionService.create(..., recurring=(rid, date))`, with `created_via="recurring"`. Each occurrence is recorded **once**: `transactions` has a unique index on `(recurring_id, recurring_date)`, so several workers or repeated visits are safe. Due occurrences are recorded in three places: when the user opens the dashboard, transactions or recurring pages (or lists/creates via the JSON API), and by `app/recurring_runner.py`, a background loop started in `main.lifespan` in every worker (`settings.recurring_interval_minutes`, default 15, 0 turns it off; the first run waits a minute). A rule that cannot be recorded (an account that can no longer be posted to) keeps its `last_error` and retries on the next run. **Skipping one occurrence** (`RecurringService.skip_next`, `POST /api/recurring/{rid}/skip`, the "Skip <date>" button on the edit page, MCP `skip_recurring_occurrence`): nothing is recorded for the next occurrence and the rule moves on to the one after; the skipped day is kept in `skipped_date` (not `last_date`, which stays "last recorded"), so editing the rule continues after whichever of the two is later and never revives it; only a running rule can skip, it clears a stuck `last_error`, and skipping the last occurrence before `end_date` ends the rule. Pausing then resuming skips what fell due meanwhile; editing continues after the last recorded or skipped day; deleting keeps the recorded transactions (their link is cleared); an account used by a rule cannot be deleted. Web: `/recurring` (list, new, edit with pause/resume/delete); JSON API: `/api/recurring`; MCP: `list_recurring`, `create_recurring` (simple, or `postings` for a split), `stop_recurring`, `skip_recurring_occurrence`. "Today" follows `FINODE_TIMEZONE`.

### Two levels

Accounts go **two levels below a top-level account, for everybody and every type**: `Expenses › Food › Groceries` is a category and a subcategory and the deepest there is (`MAX_ACCOUNT_DEPTH = 2` in `services/account.py`; it is not a setting and there is no per-person limit). `AccountService._check_depth` enforces it when creating or moving accounts (a moved subtree counts its own height, and a cycle is reported before depth), the account forms and the quick-account sheet hide parents with no room left (`_parent_options`), an account page offers "Add sub-account" only where there is room, `DataService._plan` refuses deeper imports with their line number and a restore refuses a deeper backup. Migration `a5c7e9b1d3f6` dropped `profiles.max_depth_*` and refuses to run (changing nothing) while an account is deeper; older backups' depth limits are read and ignored. Templates and the budget/categories trees therefore only ever nest a group once (a group's rows are all leaves). Any new place that creates accounts outside `AccountService` must check the depth itself.

### Limits and rate limiting

Per person (`settings.max_*`, 0 = no limit; checked by `limits.ensure_room`, which raises `LimitReached`, a `ValueError` with a message that says what to do): accounts, transactions in total, new transactions a day (not counting recurring rules or imports), postings in one transaction, and the size of a restore upload (imports stay at 5 MB). Imports and restores check them up front and report "too big for your limits" before anything is saved; services enforce them for everything else, so any new way of creating accounts or transactions must go through a service or call `ensure_room` itself. Sign-in and sign-up attempts are slowed per address (failed sign-ins also per email, `FINODE_LOGIN_ATTEMPTS`, `FINODE_SIGNUP_ATTEMPTS` in a `FINODE_ATTEMPT_WINDOW_MINUTES` window) by the in-memory `ratelimit.attempts` (per process, answers 429 with `Retry-After`). The client address comes from the proxy headers (`fastapi run --proxy-headers`, `FORWARDED_ALLOW_IPS` in compose); if that stopped working everybody would share one address, so keep it. Tests clear the counters automatically (`tests/conftest.py`).

### Erasing and leaving

Profile › Your data has two destructive actions (the person types their email to confirm; `confirm_word`): **Erase my books** (`POST /profile/data/erase`) and **Delete my account** (`POST /profile/data/delete-account`, only offered when `settings.can_delete_logins`, that is when the Supabase service key is configured). `services/erase.py` (`EraseService`) walks **every table that has a `user` column**, children first (`SQLModel.metadata.sorted_tables`), so a new table is erased without anyone remembering it; clearing the books keeps `profiles`, `api_tokens` and `oauth_grants` (what belongs to the person, not the books), deleting everything keeps nothing. Deleting the account erases everything first, then removes the Supabase login (`signup.delete_user`); if that call fails the books are already gone and the person is told to retry. Deleting the profile row also frees a place under `FINODE_MAX_USERS`. These routes are classified `OWN_DATA` in the isolation audit. Flash keys are one global dictionary: check a new key is not already taken.

### Isolation audit

`tests/test_isolation.py` is the guard for multi-user use: person A has a ledger that uses every feature, person B signs in and tries to reach it by every route that takes an id (all must answer 400/403/404 and nothing of A's may come back, A's books unchanged afterwards), by every list and page (only B's data), by naming A's accounts, categories, recurring rules or private assets inside B's own requests (API and forms), through B's assistant token, and without any sign-in. `test_every_route_is_covered` fails when a route is added that is not classified there (`PUBLIC`, `LISTS` or `REFERENCES`; routes with an id are swept automatically), so a new endpoint cannot ship without deciding what it does with other people's data. Every query must be filtered by the user (`self.uid` in repositories); the audit was checked by removing that filter from four repositories, and it failed each time. Keep A's names out of static template text (the audit looks for them in B's pages).

The interactive API docs (`/docs`, `/redoc`, `/openapi.json`) are off unless `FINODE_API_DOCS=true`.

### Queries per page

The database is hosted (about 16 ms a round trip), so **a page must not query once per account or once per row**: that made the new-transaction page take 3.8 s (218 queries) until balances were computed from one query. Rules: list balances from `AccountService._postings_by_account` (one query for every posting, `list()` passes it to `_to_read`), lists of transactions load postings with `TransactionRepository.postings_for_transactions` and transactions with `read_many`, never `read(tid)` or `postings(tid)` in a loop. **The session remembers repeated reads** (`repositories/cache.py`, `remembered`): the account list, the profile, the budget targets and plan, and postings are loaded once per request however many services ask, and forgotten on any write (flush, commit, rollback, a non-SELECT statement) and while the session holds unwritten changes, so a read never shows what was true before a write in the same session. Its results are shared: copy a list before sorting it in place. New repository reads that several services repeat belong there; a new write path needs nothing (flush and commit are hooked). In the test suite the shared session forgets at the start of each request (`conftest.client`, `tests/browser/conftest.py`), as each production request has its own. A transaction's postings are checked against one account list, never one query per posting. Responses are gzip-compressed (`caching.Compression`; fonts and images pass through). `tests/test_query_counts.py` counts the statements of the main pages with small and larger books, fails when the count grows with the data and holds each page under a ceiling (`CEILING`: lower it when a page gets cheaper, raise it only with a reason); `tests/test_read_memory.py` guards the memory. To measure on real data without touching production: restore the latest dump into a scratch Postgres, point `FINODE_DATABASE_URL` at it and count statements with an SQLAlchemy `before_cursor_execute` listener.

### Recent and ordered accounts

`accounts.position` (migration `b8d0f2a4c6e1`; `accounts.pinned` was added with it and dropped again by `b6d8f0a2c4e7`: nothing could be pinned any more, and the API's `pin`/`unpin`, the backup field (older files' `pinned` is read and ignored) and the field in account data went with it). **Recently used** lists the five accounts last used by hand (`AccountRepository.recent_account_ids`: newest transaction by `created`, leaving out recurring rules, imports and anything that touches Opening Balances, so creating an account is not "using" it; closed and system accounts are skipped) as cards at the top of the accounts page (`data-quick`, hidden while searching). **Order:** siblings are alphabetical until moved; `AccountService.move` (`POST /accounts/{aid}/move`, Move up / Move down on the account page) writes the group's current order into `position` 0..n-1 and swaps one place, `reset_order` clears it ("A–Z"), a new account (no position) lists after the placed ones, and moving an account to another group forgets its place. `AccountService.order_key` is the one sort key, used by the accounts page and pickers (`build_tree`) and by the budget's category lines, so ordering an Expenses account also orders the budget. The backup carries both fields (a closed account is restored unpinned).

### Period lock

`profiles.locked_through` (Settings › Period lock, `POST /settings/lock`, `PATCH /api/profile/` with `locked_through`; a day before today at the latest, null removes it) closes the books up to and including a day. `services/lock.py` (`locked_through`, `refuse_locked`, `LockedPeriodError`) is the one check: `TransactionService` refuses to create, change (the old date and the new one) or delete anything dated in it (`LockedPeriodError` is an `InvalidPostingError`, so the API answers 400), the budget refuses to assign, move, copy or fund a month that **ends** inside it (`BudgetService._check_open`), recurring rules leave out occurrences that fall in it (recorded as `skipped_date`, the rule carries on, no error), and the edit page shows a notice with Save and Delete disabled. Not held up by it: imports and restores (they only fill an empty ledger and write through the repositories) and account opening balances and balance adjustments (dated today, which is always after the lock). Erasing the books clears it; the backup carries it. New code that writes transactions through anything but `TransactionService` must call `refuse_locked` itself.

### Month summary

`/summary?month=YYYY-MM` (web, `routers/web/summary.py`, `summary.html`; the dashboard's month card links to it) (`ReportService.month_report`, `MonthReportRead`): a month's income, spending and left over, the savings rate (net as a percentage of income, none when nothing came in), spending and earnings per **top-level account** below Expenses/Income (group totals, largest first, with the month before for comparison and each one's share), and the totals of the six months ending with it for a plain CSS bar chart (no JavaScript library). It is computed from postings in one pass over the six months, like `summary` and `breakdown`; transfers and Equity are neither income nor spending. The current month counts up to today and is never compared with a whole month (the page shows last month in full instead of up/down); months that have not started are refused (the page redirects to this month). It reads the books only, so nothing else needs to know about it.

### What day it is

Never call `date.today()`: use `clock.local_today()` (and `local_now()`, `local_midnight_utc()` for the per-day limit). `FINODE_TIMEZONE` (an IANA name such as `Asia/Kolkata`, validated at start-up) is the zone "today" is read in for the whole installation, so entries, the recurring runner, the budget's current month and "Today" in lists follow the people's clock and not the server's; unset, the server's own clock is used. Timestamps stay in UTC. It is per installation, not per person: a person in another zone would need a profile column and the recurring runner would need each rule's owner's zone. Dependency `tzdata` is there so the slim Docker image has zone data.

### Forgotten passwords

### Double-entry ledger

`app/models/account.py` defines accounts as a tree. Each user has five system
root accounts (`Assets`, `Liabilities`, `Equity`, `Income`, `Expenses`),
created lazily on first access by `AccountService._ensure_roots` (a partial
unique index on `(user, name)` where `parent_id IS NULL` keeps this race-safe).
There is no stored type: an account's type is its root ancestor, and all
non-root accounts require a `parent_id`. Roots cannot be renamed, moved, or
deleted. Categories are not a separate table; former category concepts are
represented as income or expense accounts.

`app/models/transaction.py` defines `Transaction` and `Posting`. A transaction
contains at least two postings, every posting has a positive amount, and total
debits must equal total credits. The service layer validates those invariants
and verifies that all referenced accounts belong to the authenticated user.
Postings may not target root accounts. Asset and liability accounts that have
sub-accounts cannot be posted to either (and cannot gain sub-accounts once they
have postings), but Income and Expenses groups can (`GROUP_POSTING_ROOT_NAMES`
in `app/services/account.py`). An account cannot be moved under a different
root (that would silently reclassify its history).

Account balances are derived from postings. Assets and Expenses increase
with debits; Liabilities, Equity, and Income increase with credits. Asset and
liability accounts that already have postings cannot gain sub-accounts. Opening balances and
direct balance edits are posted against the system equity account named
`Opening Balances`, which cannot be renamed, moved, deleted, given
sub-accounts or have its balance set directly.

### Edges of what is accepted

Checked by `tests/test_ledger_edges.py`, and by `tests/test_ledger_fuzz.py` (random sequences of operations, then every balance recounted from the stored postings, the trial balance, a backup and restore, and the budget's identity `ready_to_assign = money_in_accounts - reserved_for_cards - available - assigned_to_later_months`). **Dates**: every day a person can enter (a transaction, a recurring rule's start and end, a target date, the period lock, a budget month, the same fields in a backup) must lie between `clock.FIRST_DAY` (1900-01-01) and `LAST_DAY` (2999-12-31): use the `Day` type in `schemas/day.py` for a new date field. Past either end the calendar arithmetic ("the month before") could fail at year 1 or 9999, and one entry dated 9999-12-31 used to turn every page into an error. `BudgetService.month_start` refuses a month outside the span (`BudgetError`, 400 in the API); `first_of_month` is the unchecked version for dates already stored. **Computed figures** (balances, totals, the budget's figures: the `Read` models) have no digit limits, because a sum of valid amounts may be longer than one amount can be (a limit there made every page an error); only an input amount is limited (16 digits before the point, 8 after, then the currency's decimals). **Text**: a NUL character cannot go into Postgres, so `models/utils` drops it from every string on every write (a `before_flush` hook) and `TransactionRepository.list` from the search text. An account's name is trimmed, visible, on one line and without `:` (`schemas/account.clean_name`), and **unique among its siblings, capitals aside** (`AccountService._check_name_free`; a journal import is case-sensitive like the format and may still create `Food` and `food`); a payee is one tidy line and a blank payee or note is none. **One entry, one direction**: an account may not be on both the debit and the credit side of one transaction (`TransactionService._resolve`; several rows of the same side are fine). **Budget**: `assign` may be negative to take back what an earlier month left in a category (that is what Move money writes too) but never more than the category has left (`BudgetService.assign`), otherwise Ready to assign would exceed the money there is.

### Ledger integrity

- **Database checks:** `postings` has `CHECK` constraints (`amount > 0`, `value > 0`, `side IN ('DEBIT','CREDIT')`), added by migration `a3c5e7f9b124`, which refuses to run if existing rows break them. Balance and "at least two postings" cannot be a plain check, so they live in `TransactionService._resolve`; `ReportService.trial_balance` (`/api/reports/trial-balance`, MCP `check_books`) re-checks every transaction from the stored rows and names the ones that fail. Any new code path that writes transactions must keep a test asserting `trial_balance().balanced`.
- **Posting ids are stable:** `TransactionRepository._replace_postings` updates postings in place on edit (matching first on account and side, then on account), adding or removing only what is left, so anything that refers to a posting keeps working.
- **History:** `transaction_history` is append-only (no foreign key, so a deleted transaction's trace survives it). `TransactionRepository` appends a row on create, update (skipped when nothing changed) and delete, so every path (web, API, import, recurring, MCP, balance adjustments) is covered; the row holds the transaction as it stood after the action. Read it with `TransactionService.history(tid)` / `.deleted()`; the edit page shows it. Never update or delete history rows.
- **Balances by date:** account balances count postings dated up to `as_of` (today by default, so future-dated entries do not count yet; `?as_of=` on `/api/accounts`). The register still lists every entry.

### Budget (envelope budgeting)

`services/budget.py` (`BudgetService`) gives every unit of money a job, YNAB-style, **on top of the ledger without changing it**. The only stored things are the plan (`budget_allocations`: user, month = first day, expense account, amount; unique per month and account) and the flag `accounts.on_budget` (asset or liability accounts holding a currency; new asset accounts holding a currency default to yes, a card is opted in; the migration switched on existing asset leaves). Everything else is derived on demand, so editing the ledger can never leave it stale:

- *cash* = debits minus credits on the budget's accounts (a flagged credit card counts as money owed), up to the month's last day; flagged accounts with sub-accounts are left out (still listed as `ignored_accounts` in the API, no longer on the page);
- *activity* of a category (an Expenses account) = postings to it in transactions that touch a budget account (spending from outside the budget is ignored);
- *available* rolls month by month (`BudgetService._roll`): `max(0, last month's available) + assigned - activity`. Leftovers carry forward, but an overspent category (negative at the end of a month) starts the next month at **zero** and the deficit is taken out of *ready to assign* from then on (cash overspending, the YNAB way; credit-card purchases are treated the same). In its own month an overspent category just shows negative and ready to assign does not change yet. `overspent_last_month` reports what was deducted;
- *ready to assign* = cash minus the sum of all categories' available. Moving money between categories (`move`, limited to what is available) never changes it.

Budgeting **starts with the first month anything was assigned** (`start` in `_compute`): earlier spending is ignored, because cash is the balance now and past spending already left it (counting it as overspending would deduct it twice). Spending paid from an asset/liability account that is not part of the budget (typically a credit card never switched on) is not counted in a category; it is reported as `left_out` / `left_out_accounts` and the page offers "Add to budget" per account (`POST /budget/accounts/{aid}/include`).

**Loans and other accounts outside the budget:** an asset or liability account that is not part of the budget can name a *payment category* (`accounts.payment_category_id`, an Expenses account; set on its edit page or `PATCH /api/accounts/{aid}` with `payment_category_id`, null removes it; joining the budget clears it; deleting the category clears the link). Debits to such an account in a transaction that touches a budget account count as spending in that category (credits, such as a loan paying out, do not), so paying an EMI spends the category instead of silently lowering Ready to Assign. The Categories page and a category's own page count and list these payments too (`AccountService.payments_into_loans`, used by `register` and `ReportService.account_totals`, the same rule: debits only, in transactions that touch a budget account); so do `breakdown`, the Month summary (`month_report`, its six-month trend) and `ReportService.summary` (the overview's expenses): every report counts the EMI once, as spending in the payment category (`tests/test_loan_payments.py` compares them). What the lender charges (interest, posted loan credit -> interest expense) touches no budget account and stays out of the budget (the reports, which count every posting to an expense account, do show it as the expense it is), and the account is not offered in the left-out notice.

**Setting up a month:** `BudgetService.copy_previous` (web "Copy last month's amounts", `POST /budget/copy`, MCP `copy_budget_from_previous_month`) assigns the month what each open category got the month before, only where nothing is assigned yet; `BudgetRead.copyable` is what it would copy. Money assigned to **later months** is subtracted from ready to assign in every month before them (`assigned_to_later_months`), so assigning ahead (by opening the next month and filling it in) uses up what is ready to assign now, and the same money reads the same from either month.

**Credit cards** (liability accounts that are part of the budget) are listed in a "Credit card payments" block above the categories: *to pay* is what is owed at the month's end (`BudgetCard.owed`, zero for a card in credit), with the month's *charged* and *paid*. Nothing needs assigning: it is the same arithmetic as before (a card's debt is subtracted from cash), now made visible, and `ready_to_assign = money_in_accounts - reserved_for_cards - available - assigned_to_later_months` always holds (`BudgetRead`; the page and `get_budget` show the sum).

Groups show the sum of their subcategories; a group posted to directly also gets an "(other)" row. Deleting a category deletes its plan rows. Web: `/budget?month=YYYY-MM` (inline assigning swaps `partials/budget_body.html`, `/budget/move` page), the account edit page has the "Part of the budget" checkbox; JSON API: `/api/budget/`, `PUT /api/budget/categories/{aid}`; MCP: `get_budget`, `assign_to_category`, `move_budget_money`. 
**Notes:** a category can carry a short note (200 characters), kept as the expense account's `details` (so it is in backups, on the account's edit page and shown under the name on the budget; `BudgetLine.note`, groups included but not their "(other)" row). Set on the category's target page (`POST /budget/note`; empty removes it); `get_budget` shows it, the assistants cannot change it.
**Targets** (`budget_targets`, one per category: `kind`, `amount`, `target_date`; only the wish is stored): `monthly` needs the amount assigned each month (`weekly` and `yearly` below), `refill` keeps the amount available (needs amount minus what carried in), `by_date` saves the missing money evenly over the months left including this one, the whole rest once the date's month arrives (`services.budget.funding`; *carried in* = available - assigned + spent). A line reports `target`, `needed` and `underfunded` (groups sum their children); `BudgetRead.underfunded` totals them. `BudgetService.fund(month)` assigns the underfunded amounts in display order until ready to assign runs out. Web: `/budget/target` form, "Assign what is needed" button (`/budget/fund`); API: `PUT/DELETE /api/budget/categories/{aid}/target`; MCP: `set_budget_target` (kind `none` removes), `fund_budget_targets`. **Weekly and yearly targets:** `weekly` needs `amount` once for each `weekday` (0 = Monday, `budget_targets.weekday`) in the month (`weekday_count`), assigned like a monthly one (carried-in money is ignored); `yearly` is `by_date` that repeats: `target_date` only matters by its month, and `due_month` takes the next such month, this one included, so once it has passed the target looks at next year and saves `amount` over the twelve months again. A `by_date` target whose month has passed and is still short is `overdue` (`BudgetLine.overdue`, "overdue, needs X more" on the page, `overdue` in `get_budget`); a yearly target just rolls on and is never overdue. **By week:** a category with a weekly target lists the month week by week (`BudgetLine.weeks`, `weeks_of`: weeks start on the target's day, the days before the month's first such day are a first row funded last month with no allowance, the last week stops at the month's end), each with what was spent in it against the target amount, the current week marked and an overspent week in red; the page shows it under "By week" (`details.weeks`) and `get_budget` lists it. Spending is read from the ledger per day (`daily` in `_compute`); nothing is stored and nothing rolls over between weeks. MCP `set_budget_target` takes `weekday` (Monday…Sunday) and `by` (the month, for by_date and yearly); the backup carries `weekday`.
